# Optimization scope

- Optimize the production Fusion Local Exposure runtime path, primarily for Snapdragon 8 Gen 1 / Adreno 730.
- Exclude visualization, debug outputs, comparison images, and viewer presentation from production cost and optimization benefit claims. Removing viewer-only work is not an algorithm optimization.
- The current `apply_exposure` entry mixes production exposure/tonemapping with viewer-only baseline-color and exposure-map outputs. Do not attribute the whole entry's cost to production. `compute_main` is viewer presentation and is excluded.
- Existing viewer-derived offline baselines are useful compiler records, but are not isolated production-path performance measurements. State this limitation when interpreting them.
- The user now authorizes approximate optimization when it does not noticeably affect visual quality (goal-mode request). Preserve the original lossless control, quantify errors and inspect representative images before retaining approximate candidates. Do not introduce value-specific fast paths such as reusing tonemapping only when exposure equals exactly one.
- Offline compiler statistics do not establish phone frame time or sustained performance. Validate performance claims with appropriate production-path measurements when available.
- The Android workflow is `python -m tools.profiling.android.benchmark`. It times `apply_exposure_production`, excludes viewer outputs, bypasses caches, and separates whole-chain timestamps from per-pass diagnostics. See `docs/performance/android.md`.
- The currently measured phone is NX789J / SM8750 / Adreno 830, not Adreno 730. Never relabel its timings as 8 Gen 1 results. Same-phone parity and desktop portability are distinct checks; the initial 1080p run has an unresolved desktop-portability warning near the inverse curve's white endpoint.
- For game-format bandwidth estimates, use R11G11B10 HDR input, RGBA8 sRGB color-attachment output and 45 FPS. Report bytes/frame and nominal average GB/s separately from active effective throughput; neither is a hardware DRAM traffic measurement. Include Fusion intermediates before claiming total algorithm traffic.
- The opt-in fused production graph is `--fused-guided` in the Android benchmark (`shaders/fusion_compact.slang`). It preserves FP32 storage precision while packing six useful pyramid channels into RGBA32F + RG32F and fusing guided reconstruction in a 16x16 tile. Validate against the full unfused graph; do not infer real DRAM reductions from the sweep model or claim the 1.5 ms target without matched phone evidence.
- The retained approximate algorithm is `--variant gather-reduction`: RG16F exposure differences relative to a separately preserved FP32 middle exposure, RG16_UNORM weights, precomputed low-resolution EV, full 4x4 Gather reduction with odd-size fallback, and the original 5x5 guided supports with separable FP32 sums. Four phone scenes, exposure stress and desktop moving-edge checks passed fixed gates. Nominal incremental sweep traffic is 0.863 GB/s at 1080p/45 FPS, not measured DRAM. See docs/performance/twohour-optimization.md. The older half-aux-compute is the session's independent starting candidate; reduction4/radius1/mobile and other failed research presets are not accepted optimizations.

- A subsequent graphics-context audit invalidated extrapolation of the ~0.6 ms compute-only increment to a game: one real graphics draw causes persistent compute slowdown in the same Vulkan process. The foreground NativeActivity with graphics + actual present measured ~2.81 ms incremental for half-aux-compute; present without a graphics draw remains fast. Cause is unresolved. Use matched graphics-context measurements for new game-performance claims; never claim the 1.5 ms target is already met from the older headless tables.
- Use `activity --hdr-producer --joint-submission` for a graphics-produced HDR input without a CPU fence gap before postprocess. Joint timestamps include the same graphics producer in both Fusion and baseline intervals; separate-submission core timestamps exclude it. Do not mix total-time definitions or output backends. Also inspect complete-chain cost: larger output workgroups can reduce both Fusion and tonemap totals while increasing their difference. The viewer remains the original independent reference.
- RG16F residual quality is validated for the default Sigma=0.2, not all weight settings. Sigma=0.05 with ±3 EV brackets failed a moving-edge error-pixel gate; RG32F residuals fixed that desktop case, whereas FP32 averaged coefficients did not. Preserve this limitation when exposing parameters or making precision claims. See the parameter-scope section of the two-hour report.
